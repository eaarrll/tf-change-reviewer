# Research: Terraform JSON plan format (Terraform 1.10–1.17, OpenTofu 1.13), verified against source and real runs

SUMMARY: I checked the JSON plan format three ways. First, I read the Go source at Terraform v1.10.5 and v1.17.2 (the latest tag) and at OpenTofu v1.13.10. Second, I traced how fields and FormatVersion changed across every Terraform tag from 0.12 to 1.17. Third, I generated real plans with the local Terraform v1.10.5 and diffed them. Those plans used the built-in terraform_data resource, plus the user's already-cached aws 5.100.0, null and local providers, run offline against hand-written state. Where the docs and the code disagree, the code and the observed output win.

The format has been "1.2" since Terraform 1.5 and is still "1.2" in 1.17.2. Several fields arrived later without a version bump: errored, applyable/complete, deferred_changes, index_unknown, identity, action_invocations, and the forget / forget,create actions. A consumer cannot use format_version to detect these features.

For lineage, the JSON reliably gives five links:

- the replace trigger: action_reason plus replace_paths (an array of paths; each step is a string or an integer);
- before/after values, so you can find the exact changed sub-path;
- per-attribute expressions: either {constant_value} or {references:[...]};
- the module_calls tree, where each input is keyed by the child module's variable name;
- root variable values (plan.variables), and relevant_attributes, which is Terraform's own list of the resource attributes that feed each change.

The JSON never contains:

- locals;
- source file/line positions;

   IMPLICATIONS:

- Lineage algorithm, step 0, validate: parse format_version as major.minor. Reject a major other than 1, and accept any minor since fields were added inside 1.2. Read errored, applyable and complete; treat a missing applyable/complete as "probably OpenTofu" (heuristic). If complete==false (e.g. -target), report that the plan is partial.
- Lineage algorithm, step 1, select candidates: keep resource_changes where actions is not ["no-op"]. Treat as destructive any actions containing "delete", and as orphaning any containing "forget". A 2-element array is a replace: ["delete","create"] means downtime, ["create","delete"] means create_before_destroy, and forget,create / create,forget mean the old object is orphaned. Also handle deposed entries, and data-source ["read"] entries with read_because_*.
- Lineage algorithm, step 2, branch on action_reason:
- replace_because_cannot_update: use replace_paths.
- replace_by_triggers: no paths; parse lifecycle.replace_triggered_by from HCL, then check that the referenced resource has its own change.
- replace_by_request: out-of-band `-replace` flag; the PR is not the cause.
- replace_because_tainted: state-level; not the PR.
- delete_because_no_resource_config / no_module: a removed resource or module block in the diff (HCL/diff).
- delete_because_count_index / each_key / wrong_repetition / enabled_false (OpenTofu): follow count_expression / for_each_expression references.
- read_because_*: a data source deferred by unknown inputs or pending dependencies.
  Treat any unknown reason value as unspecified.
- Lineage algorithm, step 3, map the instance to config: parse address and module_address with a real address parser that handles quoted keys with escapes, e.g. module.svc["a"]. Strip the instance keys and walk configuration.root_module.module_calls[name].module, one level per module segment. Find the resource whose module-relative address equals `type.name` (or `data.type.name`). Keep the instance key, so each.key / count.index can be resolved later.
- Lineage algorithm, step 4, narrow the path: for each replace_paths path P, walk change.before and change.after along P. Then recursively diff the subtrees below P to find the concrete changed leaf (e.g. triggers_replace.major). If after_unknown is true at P, the cause is an upstream unknown (a cascade). In that case jump to referenced resources that are themselves being replaced or created, and cross-check against relevant_attributes. If resource_drift has the same address and the value at P changed between drift before and after, mark the cause as drift, not the PR.
- Lineage algorithm, step 5, path to expression: walk resource.expressions with P. A string step indexes the map. An integer step indexes a block array, but only when the next node is an array; that alignment is valid only for static list blocks. Stop at the first expression node ({constant_value}|{references}|{}), because granularity is per attribute. If a block step is missing from expressions, assume a dynamic block and fall back to HCL. If the node is {}, the expression is a function call with no references; fall back to HCL.
- Lineage algorithm, step 6, classify each reference string. Use the longest form for display and the shortest (the subject) for graph edges, and deduplicate:
- var.X → step 7.
- local.X → HCL needed; locals are not in the JSON.
- module.M.out or module.M["k"].out → recurse into module_calls[M].module.outputs[out].expression, scoped to the child.
- <type>.<name>[...] and data.* → upstream resource; check its resource_change and prior_state.
- each.* / count.* → instance key plus the parent's for_each/count expression.
- path.* and terraform.workspace → environment.
- Lineage algorithm, step 7, cross module boundaries: inside a child module, var.X maps to the parent's module_calls[child].expressions[X]. Recurse in the parent's scope until the root. At the root, var.X has its value in plan.variables[X].value and its default in configuration.root_module.variables[X].default. The plan does not contain the previous run's variable values. To find where the value came from, search the PR diff for `variable "X"` default changes, *.tfvars / *.auto.tfvars assignments and CI env (TF_VAR_X); otherwise label it out-of-band.
- Lineage algorithm, step 8, prune by value: wherever a value is available, drop candidate references that did not change. Root variables come from plan.variables; resource attributes from resource_changes before/after, prior_state and planned_values; root outputs from output_changes. Child-module variables, locals and child outputs have no values in the JSON. For those, either evaluate locally (HCL plus function evaluation) or keep them as unpruned candidates with lower confidence.
- Lineage algorithm, step 9, attach file/line (HCL-only): parse the head and base revisions of every module directory with a position-aware HCL parser, such as tree-sitter-hcl/WASM in TypeScript. Index by (module dir, block kind, block labels, attribute path) → byte range and line range. Intersect with the PR diff hunks on both sides, the head side for added/changed lines and the base side for deleted ones. Rank chains in which a diff hunk sits on the chain. Link both ends: the resource attribute line and the root-cause input line.
- Lineage algorithm, step 10, handle the non-expression root-cause classes, all from the diff or HCL rather than plan expressions:
- a module source or version_constraint change (the plan has only the new module_calls.source/version_constraint; the resolved version lives in .terraform/modules/modules.json);
- a provider or lockfile upgrade (.terraform.lock.hcl): suspect it when a replace_paths attribute has no changed lineage;
- a moved block (previous_address);
- a removed or import block;
- lifecycle edits (create_before_destroy, prevent_destroy, ignore_changes, destroy=false).
- Masking before the LLM: build a sensitive-value set from four sources:
- plan.variables values whose configuration variables[].sensitive is true (and ephemeral variables, found via HCL in Terraform);
- every leaf marked by before_sensitive/after_sensitive in resource_changes and resource_drift;
- output_changes flagged sensitive;
- prior_state sensitive_values.
  Then scrub by both path and value equality across the whole document, which catches unmarked derived copies like output.password. Drop or replace all provider_config expressions constant_value. Mask configuration constant_value at attribute paths that any instance of that resource marks sensitive. Do not use planned_values.sensitive_values for masking. Safer default: send the LLM the structural lineage plus hashed or redacted values and a 'changed: yes/no' flag, never raw values.
- Parser robustness (TypeScript types): make every field optional. Allow before_sensitive/after_sensitive to be false, true or an object, and after_unknown to be a boolean or an object. Accept unknown action arrays and action_reason strings. index can be a number or a string, and index_unknown may be present. Ignore unknown top-level keys such as action_invocations, deferred_action_invocations, before_identity and after_identity. Treat replace_paths as an unordered set, and treat references as an ordered multiset compared only by string equality.
- Risk-scoring features available deterministically from JSON:
- action class (replace, delete, forget, create_before_destroy);
- action_reason;
- resource type criticality (e.g. aws_db_instance, aws_rds_cluster);
- number of replace_paths;
- whether the replace cascades (after_unknown on dependents, relevant_attributes fan-out);
- drift-caused or PR-caused;
- out-of-band cause (replace_by_request, tainted, variable not in diff);
- the plan's complete flag.
  prevent_destroy and create_before_destroy cannot be confirmed from config JSON (lifecycle is absent). Read them from HCL; only the ["create","delete"] ordering reveals create_before_destroy indirectly.
- Evaluation data: build fixtures with terraform_data (triggers_replace gives deterministic replace_paths with no cloud). Use crafted-state plus -refresh=false plans with real providers for realistic replace_paths, e.g. aws 5.100.0 gives [["s3_import",0,"bucket_name"]]. The scratchpad experiments are templates for a golden test corpus covering both Terraform and OpenTofu.
