# Research: mapping lineage to HCL source and the PR diff; plan inputs in CI

Mapping plan-JSON lineage onto source files and the PR diff. The Terraform JSON plan has no file, line or range data anywhere. I confirmed this three ways: the HashiCorp docs, the jsonconfig Go structs, and a local Terraform 1.10.5 plan in which a grep found no position keys. The JSON's `configuration` block is also lossy in ways that matter for lineage. Expressions keep only `constant_value` or `references`, never their source text. An expression made only of a function call disappears: I saw `for_each = toset([...])` produce no `for_each_expression`. Dynamic blocks are excluded (per the docs), and the `lifecycle` / `replace_triggered_by` settings are not represented. A `replace_by_triggers` replacement came back with no `replace_paths`. So the tool has to parse the .tf files itself. Recommendation: use web-tree-sitter with the `.wasm` grammar from `@tree-sitter-grammars/tree-sitter-hcl` (about 460 KB in total, MIT/Apache-2.0, no native deps, gives row and column positions). Handle `.tf.json` files with jsonc-parser, and keep a Go-to-WASM build of hashicorp/hcl `hclsyntax` as a fallback if fidelity problems appear. Map module addresses to folders with `.terraform/modules/modules.json` or the `tfconfig/modules.json` inside the binary plan, falling back to resolving relative `source` paths. A local binary plan file is a zip that holds a full config snapshot, including remote modules, plus `.terraform.lock.hcl`. That is useful extra input, but HashiCorp calls the format opaque. For the diff, use local `git diff --no-ext-diff --no-color -U0 -M <merge-base> <head>`, which is what GitHub's three-dot view shows, and fall back to `pulls.listFiles` (at most 3000 files; `patch` may be omitted). Links: permalinks take the form `blob/<head_sha>/<path>#Lx-Ly`. Files-changed anchors take the form `#diff-<sha256(path)>R<line>`; I confirmed this by hand against a live PR, but GitHub does not document it. Plan changes that come from outside the diff (tfvars, TF_VAR_/CLI/workspace variables, module or provider version bumps, drift) need a separate step that attributes each change to a cause and states its confidence, because the plan JSON records no variable sources and no provider versions. For inputs, the Action should accept a glob of plan JSONs, each tied to a root folder (a manifest or Terragrunt-style layout inference). It can optionally take a binary plan plus a working folder (it then runs `show -json` itself in an initialized folder) or an HCP Terraform run ID. It should reject wrapper-polluted JSON with a specific error.

## Findings

- **[high] The Terraform JSON plan (`terraform show -json`) has no file, line or range data. The machine-readable UI stream (`plan -json`) has no positions on `planned_change` either; only diagnostics carry `range` and `snippet`. Artifacts: <scratch>/tfplay/plan.json

- **[high] `replace_paths` and `action_reason` are the starting point of the lineage. - **[high] Recommended HCL locator: web-tree-sitter 0.27.2 (MIT) plus the tree-sitter-hcl grammar `.wasm` from `@tree-sitter-grammars/tree-sitter-hcl` 1.2.0 (Apache-2.0). The external scanner handles heredocs. Nodes expose startPosition/endPosition {row, column} (0-based rows) and startIndex/endIndex. API: `Parser.init({locateFile})` and `Language.load(string|URL|Uint8Array)`. For a bundled action, copy both .wasm files into dist/ and load them with fs.readFileSync. Don't install the grammar package itself: its deps are node-addon-api/node-gyp-build with an install script; just vendor the .wasm. Its README reports 1892/1892 real-world files parsed. Maintenance is light: last npm release 2025-06 (built with tree-sitter-cli ^0.25.6), last commit 2026-01 (.tofu extension), 147 stars, open heredoc scanner bugs #78 and #80 (non-ASCII heredoc identifiers swallow the rest of the file). web-tree-sitter >=0.25 supports parser ABI 13–15, but its README warns that "Some prebuilt `.wasm` files use an older dynamic-linking format that newer versions of `web-tree-sitter` cannot load". - **[medium] A hand-written block/attribute locator is feasible but needs a real lexer with a mode stack. A Go-to-WASM build of hashicorp/hcl `hclsyntax` is the high-fidelity fallback.** — The hclsyntax spec says: comments are `#`, `//` and `/* */`. Heredocs are `<<ID` / `<<-ID`, end when the identifier appears on a line of its own (indented closers allowed), and the identifier may contain Unicode ID chars and '-'. Templates use `${` and `%{` with escapes `$${` and `%%{`, and quoted strings can nest inside interpolations (`${"${true}"}`). Labels are quoted strings or bare identifiers, and blocks can be one-line. A brace counter without these modes will mis-locate blocks. hcl/v2 `hclsyntax` returns exact hcl.Range for every Attribute (NameRange, SrcRange) and Block (TypeRange, LabelRanges, Open/CloseBraceRange), and its JSON parser gives ranges for .tf.json as well. Compiling a small Go program to WASM (as hcl2json does) gives Terraform's own parser at an estimated 2 MB gzipped (by analogy with hcl2json, not measured) and needs a Go toolchain in the build.  
  Sources: https://raw.githubusercontent.com/hashicorp/hcl/main/hclsyntax/spec.md, https://github.com/tmccombs/hcl2json
- **[medium] File set rules the locator must follow: `.tf.json` (JSON syntax), OpenTofu `.tofu` / `.tofu.json` precedence, and override files.** — OpenTofu: when `foo.tf` and `foo.tofu` sit in the same folder, only `foo.tofu` is loaded, and `.tofu.json` likewise wins over `.tf.json`. Terraform ignores `.tofu` files. For `.tf.json`, use jsonc-parser 3.3.1 (MIT, ~213 KB, pure JS; parseTree gives node offset and length) and convert offsets to lines. Override files (`override.tf`, `*_override.tf`) can redefine attributes, so check them first when locating an attribute.  
  Sources: https://opentofu.org/docs/language/files/, https://www.npmjs.com/package/jsonc-parser
- **[high] Diff ranges: run `git diff --no-ext-diff --no-color --unified=0 --find-renames <merge-base> <head>` (equal to base...head) and parse the `@@ -a[,b] +c[,d] @@` headers into new-file line ranges. GitHub PR diffs are three-dot.** — git docs: "`git diff A...B` is equivalent to `git diff $(git merge-base A B) B`". GitHub docs: pull requests use the three-dot comparison against the merge base. Observed: `@@ -4 +4 @@` means one line on each side when the count is omitted. `@@ -2 +1,0 @@` is a pure deletion; record it as a zero-width point after new line 1 so it still falls inside the enclosing block. A new file shows `@@ -0,0 +1,2 @@`. Rename detection is heuristic (default similarity 50%; `diff.renames` defaults to true). A small file that was renamed and rewritten appeared as delete plus add, while an edited rename showed `similarity index 68%` / `rename from` / `rename to`. Use `--name-status -z` (e.g. `R068\0old\0new\0`) to get paths without core.quotePath escaping. The text after `@@` is git's funcname guess; ignore it.  
  Sources: https://git-scm.com/docs/git-diff, https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-comparing-branches-in-pull-requests, local experiment: scratchpad/gitplay
- **[high] In Actions, `pull_request` checks out a test merge commit by default with fetch-depth 1. Plans are therefore often made on refs/pull/N/merge, while links must point at head-SHA line numbers.** — For pull_request: GITHUB_SHA is the "Last merge commit on the GITHUB_REF branch" and GITHUB_REF is `refs/pull/PULL_REQUEST_NUMBER/merge`. Workflows don't run if the PR has a merge conflict. Secrets are not passed to fork PRs and GITHUB_TOKEN is read-only there. actions/checkout (examples now @v7): fetch-depth "Default: 1", where 0 means full history, and the documented `ref: ${{ github.event.pull_request.head.sha }}` checks out the head instead. If the plan ran on the merge commit and the base changed the same file, merge-commit line numbers differ from head. So resolve lineage on the planned tree, then re-locate each block/attribute by its structural path (module dir + block type/labels + attribute path) in `git show <head_sha>:<path>` before building links. Cheap history: get `merge_base_commit.sha` from the compare API, `git fetch --depth=1` the base and head SHAs, then diff them.  
  Sources: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows, https://raw.githubusercontent.com/actions/checkout/main/README.md, https://docs.github.com/en/rest/commits/commits?apiVersion=2022-11-28

Per-file fields: sha, filename, status (added|removed|modified|renamed|copied|changed|unchanged), additions, deletions, changes, blob_url, raw_url, contents_url, patch (optional), previous_filename (optional). The repository limits page says: "The maximum number of files in a single diff is limited to 300". - **[medium] Link formats: permalink `https://github.com/{o}/{r}/blob/{head_sha}/{path}#L{a}-L{b}`. Files-changed anchor: `https://github.com/{o}/{r}/pull/{n}/files#diff-{sha256_hex(path)}R{line}`, with L{line} for the old side.** — GitHub docs: replace the branch with a commit ID for a permanent link, and append `#L` plus the line number. A permalink "will render as a code snippet only in the repository it originated in". The `-L` range form is what the UI's Copy permalink produces; the docs don't spell it out. The diff anchor is undocumented, so I verified it on 2026-11-24 against hashicorp/setup-terraform PR #367: sha256("wrapper/terraform.js") = d23fc4cfcb9e21564bd8d7569246c1296365b8c9d88ffdb163729bd4f1fdb46f appears in the page as `diff-d23fc4…` with suffixes like `L33` and `R…` (13 L and 14 R variants). A Stack Overflow thread reports GitHub moved from MD5 to SHA-256. URL-encode path segments. Tree-sitter rows are 0-based and GitHub lines are 1-based.  
  Sources: https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files, https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-a-permanent-link-to-a-code-snippet, https://github.com/hashicorp/setup-terraform/pull/367/files, https://kaweah.freedombox.rocks/kiwix/content/stackoverflow.com_en_all_2023-11/questions/44029061/link-to-line-in-compare-view-on-github
- **[medium] Inline review comments can only target lines in the PR diff. Lineage hops outside the diff (variable declarations, unchanged module internals) belong in the summary comment as permalinks or snippets.** — Create review comment params: commit_id (required; use head SHA), path, line ("The line of the blob in the pull request diff that the comment applies to"), side LEFT|RIGHT (LEFT for deletions), start_line/start_side for multi-line comments, subject_type line|file. `position` is deprecated. - **[high] The plan does not record where a variable's value came from: `variables.X.value` looks the same whether it came from tfvars, -var, TF_VAR\_ or an HCP workspace. Attribution has to compare the value against the repo.** — Observed: `TF_VAR_x=changed` and `-var engine_version=15` each produced only {"value": ...}. - **[high] Module version bumps: the lock file does not track modules, so upgrades within an unchanged constraint can be invisible in the diff. - **[high] hashicorp/setup-terraform (now @v4, Node 24) still installs the wrapper by default. When exitCode is 0 or 2 it just returns, so the shell sees 0 and `-detailed-exitcode` gating breaks. Older versions printed a `[command]...` line into stdout, which broke `terraform show -json > plan.json` (cdktf report: "Unexpected token c in JSON at position 1"). The action should detect a non-`{` first byte or `[command]`/`::debug::` prefixes and fail with a message telling the user to set terraform_wrapper: false.  
  Sources: https://raw.githubusercontent.com/hashicorp/setup-terraform/main/README.md, https://raw.githubusercontent.com/hashicorp/setup-terraform/main/CHANGELOG.md, https://raw.githubusercontent.com/hashicorp/setup-terraform/main/wrapper/terraform.js, https://github.com/hashicorp/terraform-cdk/issues/1020
- **[high] HCP Terraform / TFE serves the JSON plan through the API, but only to a user or team token with admin on the workspace.** — `GET /plans/:id/json-output` and `GET /runs/:id/plan/json-output` return 307 to a temporary URL with a "life of 1 minute", 204 if the plan hasn't completed, and 422 for Terraform < 0.12. "This endpoint cannot be accessed with organization tokens"; it needs a "user token or team token that has admin level access to the workspace." `/plans/:id/sanitized-plan` exists for hold-your-own-key (HYOK) workspaces (Terraform >= 1.3), with permissions not stated. With a CLI-driven `cloud` block, `terraform show -json <saved-cloud-plan>` fetches the same JSON through the backend.  
  Sources: https://developer.hashicorp.com/terraform/cloud-docs/api-docs/plans, https://raw.githubusercontent.com/hashicorp/terraform/main/internal/command/show.go
- **[medium] Atlantis, Terragrunt, Spacelift and env0 each produce plan JSON in a predictable place the CLI can consume.** — Atlantis custom `run` steps get PLANFILE, SHOWFILE, DIR, REPO_REL_DIR, HEAD_COMMIT, PULL_NUM, PROJECT_NAME, BASE_REPO_OWNER and COMMENT_ARGS. The policy-check docs say "The `show` step is required so that Atlantis will generate the `SHOWFILE`"; the documented override is `terraform show -json $PLANFILE > $SHOWFILE`. Terragrunt: `terragrunt run --all --out-dir /tmp/tfplan --json-out-dir /tmp/tfjson -- plan` writes `<json-out-dir>/<unit-rel-path>/tfplan.json` (env TG_JSON_OUT_DIR), so the unit folder can be inferred from the relative path. Unit code may run from .terragrunt-cache, so map back through the terraform.source of terragrunt.hcl. Spacelift: plan-policy input exposes `input.terraform.resource_changes`; users can run `terraform show -json spacelift.plan` and add custom input via `*.custom.spacelift.json`. env0 lists an `ENV0_TF_PLAN_JSON` system variable (a path to JSON) for custom flows; details not confirmed.  
  Sources: https://www.runatlantis.io/docs/custom-workflows.html, https://www.runatlantis.io/docs/policy-checking.html, https://docs.terragrunt.com/process/faq/how-do-i-review-plans-across-all-my-units/, https://docs.spacelift.io/concepts/policy/terraform-plan-policy, https://docs.env0.com/docs/custom-flows

## Design implications

- Lineage pipeline per resource change: (1) start from replace_paths (or the changed keys of before/after when there are none) plus action_reason. (2) Strip instance keys from the address to get the module key and resource config address. (3) Find the module folder via modules.json, the plan zip's tfconfig/modules.json, or relative `source`. (4) Find the resource block, then the attribute or nested block path, with tree-sitter and take the expression text and range. (5) For each reference from the plan JSON (or extracted from the parsed source): var.X goes to the `variable "X"` block, then the parent's module block attribute X, then recurse. local.Y goes to the locals attribute; resource refs go to that resource's block. (6) Root var.X goes to tfvars/default/external. (7) Mark each hop whose range overlaps a diff range and report the deepest changed hop plus the full chain.
- Use a single `SourceIndex` keyed by (moduleDir, blockType, labels[], attributePath[]) that returns {path, startLine, endLine, side}. Build it twice: once on the planned tree (semantics) and once on `git show <head_sha>:<path>` (links), so merge-commit plans still link to head line numbers. Build a third index on base SHA files for delete actions and LEFT-side anchors.
- Parser choice: web-tree-sitter plus a vendored tree-sitter-terraform.wasm, loaded with `Language.load(fs.readFileSync(...))` and `Parser.init({locateFile: f => path.join(DIST, f)})`. Do not depend on the grammar npm package at runtime because of its native install script. Pin the web-tree-sitter version to the ABI/linking format of the grammar wasm, or rebuild the grammar wasm in our CI with a pinned tree-sitter-cli, and add a smoke test that parses a heredoc/template corpus.
- Self-check every located attribute: the identifier text at the reported range must equal the attribute name, and the tree must have no ERROR/MISSING nodes in that block. If either fails, fall back to block-level lines (resource/module block range) and lower the confidence, rather than emitting a wrong line.
- Handle .tf.json and .tofu.json with jsonc-parser offsets. Apply the OpenTofu `.tofu` precedence when the user selects tofu, and check override files before base files when locating attributes.
- Diff layer: `git diff --no-ext-diff --no-color -U0 -M <merge_base> <head_sha>` plus `--name-status -z`. Model pure deletions as zero-width points. If history is missing, get merge_base_commit from the compare API and fetch the base and head SHAs at depth 1. Fall back to paginated pulls.listFiles (per_page=100; at most 3000 files). When `patch` is missing, treat the file as changed but the hunks as unknown.
- Links: permalink `blob/{head_sha}/{encodeURI(path)}#L{a}-L{b}` for every hop, which renders as a snippet in same-repo comments. Use the Files-changed anchor `pull/{n}/files#diff-{sha256(path)}R{line}` only for hops inside the diff, LEFT/`L` for deleted lines. Use inline review comments (commit_id=head_sha, side RIGHT) only for in-diff lines; everything else goes into the summary body.
- Cause attribution should be an explicit enum with a confidence on every change: CODE_CHANGE(hop), TFVARS_CHANGE(file, line), EXTERNAL_INPUT(var), MODULE_VERSION_BUMP(call, from→to, compare URL), PROVIDER_UPGRADE(provider, from→to), DRIFT_REVERT(attrs), MOVED(previous_address, moved block line), UNEXPLAINED. Precision and recall evaluation should score the cause and the linked hop separately.
- Action inputs: `plan-json` (glob; required unless the alternatives below are given), `plans-manifest` (YAML/JSON list of {plan, root-dir, var-files[], label} for monorepos and Atlantis projects), `plan-file` + `working-directory` + `binary: terraform|tofu|terragrunt` (the action runs `<bin> show -json` in an already-initialized folder and optionally reads the zip snapshot/lock file best-effort), `var-files`, `terragrunt-json-out-dir` (infer the unit folder from the relative path), `base-sha`/`head-sha` (default from the event payload), `diff-source: git|api|auto`, and optional `hcp-run-id` + token (needs a workspace-admin team/user token).
- Input validation: the first non-space byte must be `{`. Give a specific error for `[command]`/`::debug::` prefixes (setup-terraform wrapper). Check that format_version has major 1, warn when `configuration` is missing, and record terraform_version. Docs/examples should require `terraform_wrapper: false` and warn that the wrapper swallows `-detailed-exitcode` exit 2.
- Security: plan JSON and binary plans contain cleartext secrets. Use short artifact retention, mask values using before_sensitive/after_sensitive before anything goes to the Claude agent, and never post raw values in comments. Fork PRs get no secrets, so offer a `workflow_run` two-workflow pattern: the plan job uploads an artifact, and a trusted job downloads it with download-artifact `run-id` + `github-token`.
- Atlantis/CLI mode: `tf-change-reviewer --plan $SHOWFILE --root $REPO_REL_DIR --head $HEAD_COMMIT --pr $PULL_NUM` prints markdown to stdout so Atlantis's own comment carries it. The GitHub Action wraps the same core.

## Open questions

- Can web-tree-sitter 0.27.x load the tree-sitter-hcl 1.2.0 prebuilt wasm (built with tree-sitter-cli ^0.25.6), or must we pin 0.25.x or rebuild? Not tested, because no packages were downloaded or executed in this research step.
- Does web-tree-sitter honor the Emscripten `wasmBinary` option, so esbuild can inline the runtime wasm as a binary loader instead of copying it into dist/? Not checked.
- For renamed files, does the `#diff-` anchor hash the new path? Do `R{a}-R{b}` range anchors work? Do anchors still resolve when a large file's diff is collapsed (the Stack Overflow report says no) or in GitHub's newer PR files UI? Only the single-line L/R form on one PR was checked.
- Does the plan zip's tfconfig snapshot always include remote (registry/git) module sources? Very likely, since apply needs them, but only local modules were tested. Its layout is internal, can change, and is unreadable under OpenTofu plan encryption.
- Does OpenTofu's `tofu show -json` output differ from Terraform's in ways that matter here (extra or missing keys, action_reason values, `.tofu` files in the plan snapshot)? OpenTofu isn't installed locally, so this was not tested.
- Does Atlantis's default workflow generate SHOWFILE when policy checks are off, or must users add an explicit show step? The docs only say the show step is required to generate it.
- What exact per-file size makes GitHub omit `patch` from pulls.listFiles? Undocumented; the reports are unofficial.
- Should the reviewer recommend planning the PR head SHA instead of the merge commit, which makes lineage line numbers equal link line numbers, or support both with structural re-location? The trade-off: merge-commit plans preview the merged state more accurately.
- Do HCP Terraform's sanitized-plan endpoints, or something below admin level, give enough JSON (with `configuration`) for teams that can't grant admin tokens? Not confirmed.
- How would attributions be validated in practice? We need a labeled fixture corpus (replace via module input, tfvars, TF_VAR_, module bump, provider bump, drift, moved, replace_triggered_by, dynamic blocks, for_each with functions) to measure linkage precision and recall separately from materiality ranking.
